# Option A on libxtc v1.40.1: single-fiber strand FIXED; concurrent-commit starvation REMAINS

Date 2026-08-29 (mala c6id.8xlarge NVMe, libxtc v1.40.1 rev ebc430c, PG debugoptimized).

## v1.40.1 fixed the reported bug (validated)
The libxtc v1.40.1 idle-poll-dispatch fix (exec.c: the executor's idle poll now
dispatches the io events it reaps instead of dropping them) resolves the single-fiber
fsync-completion strand I reported:
 - FORCED-OFFLOAD (XTC_AIO_FORCE_OFFLOAD=1) scale-100 init: was 100% wedge on v1.40.0 ->
   COMPLETES on v1.40.1.
 - NATIVE io_uring scale-100 init: was 1/8 wedge on v1.40.0 -> 0/8 on v1.40.1.
Confirmed the fix is compiled in (exec.c:267 __xtc_loop_dispatch_event in the idle-poll
branch; comment names the LWLock-across-fsync stranding case).

## A DIFFERENT wedge remains: concurrent-commit starvation at 64 write clients
fibers0 (pooled_protocol_carriers=0) 64-client TPC-B write load:
 - pgbench runs at 1029 tps for the first ~2s, then collapses to 0.0 tps FOREVER.
 - Server-side commits freeze (delta ~2 commits / 4s).
 - `select 1` from a fresh conn mostly RECOVERS (single-probe blips) -- so it is not a
   total hard wedge of the whole server; it is the COMMIT PATH that starves.
 - gdb: the active committer fibers are parked in
     exec_simple_query("END;") -> CommitTransaction -> XLogFlush ->
     LWLockAcquireOrWait(WALWriteLock, EXCLUSIVE) -> ProcSemaphoreWaitFiber ->
     xtc_pg_wait_fd(sem_wake_fd)
   waiting for WALWriteLock to become free (the group-commit "wait for someone else to
   flush past my LSN" path).  NO fiber holds WALWriteLock; 29-31 carrier loops sit idle in
   xtc_io_poll.  So the last holder RELEASED and the LWLock-release wake
   (LWLockWakeup -> ProcWakeSemaphore -> sem_fiber eventfd + xtc_proc_wake) to these
   parked LWLockAcquireOrWait fiber-waiters was LOST -> they never resume -> commits
   stall -> thundering-herd collapse after the first burst.

This is a DIFFERENT wake site than v1.40.1 fixed: it is the LWLock-release -> fiber-waiter
wake (ProcWakeSemaphore path in proc.c), not the aio/blocking completion resume.  It may
be: (a) another libxtc idle-poll/steal edge the v1.40.1 fix does not cover for the
sem_wake_fd readiness path; (b) a race in PG's ProcWakeSemaphore sem_fiber
arm/pending/xtc_proc_wake hand-off under many concurrent LWLockAcquireOrWait waiters; or
(c) a group-commit interaction (many waiters on WALWriteLock, one flusher, wake fan-out
losing a waiter).  Needs its own root-cause: instrument which of the parked
LWLockAcquireOrWait waiters got a ProcWakeSemaphore and whether xtc_proc_wake reached the
owning loop; capture the WALWriteLock state (held vs free) at the freeze.
