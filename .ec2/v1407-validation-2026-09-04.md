# libxtc v1.40.7 validation (2026-09-04, bene account, c6id.8xlarge NVMe)

## The reply DOES address my v1.40.6 report -- and corrects my mechanism
Team verdict: real bug, fixed in v1.40.7 (commit c4adc77).  My CLASSIFICATION was right (the
fd-park sibling of the v1.40.6 timer-park family) but my MECHANISM was wrong: the fiber was
NOT waiting on a missed WL_TIMEOUT -- it was SPINNING FOREVER inside xtc_io_del_fd walking an
io->fds list that concurrent inline unregisters had spliced into a CYCLE.  WL_TIMEOUT "never
fired" because the fiber never got far enough to observe it.  (Their gdb: one worker pinned at
io_uring.c:358 across 3 samples; TSan showed the write-write race.)
Root: v1.40.3's __xtc_io_defer_del_fd discriminator had a `!io->owner_set` clause and
owner_tid was recorded LAZILY on an io's first xtc_io_poll.  In fiber-per-session load all
sessions spawn on one home loop that keeps n_alive>0 but may never BLOCK in xtc_io_poll, so
that io's owner_set stayed 0 -> EVERY foreign session's wait_fd cleanup deleted the home io's
fd INLINE from arbitrary threads -> concurrent splices -> cycle -> infinite spin holding
WALWriteLock (+ an occasional zombie-list double-free).  Fix: record the io owner EAGERLY at
worker birth (__xtc_io_set_owner from __xtc_exec_worker + xtc_loop_run) so foreign cleanups
ALWAYS defer.  Verified present in the tag (exec.c + io_uring.c).

## Measured result: the spin IS fixed; a DIFFERENT residual hang remains
Fresh-server-per-run harness (the previous 7/8 was inflated by a half-dead-server cascade
artifact -- my harness reused one server, and after a timeout-kill it entered
"could not fork new process for connection: Function not implemented", making runs 3-8 bogus):
  CLEAN RATE (fresh server each run): 2 OK / 3 HUNG out of 5.
  OK runs: tps = 2620, 2407, (2990 in an earlier run).
So v1.40.7 materially improved it (v1.40.6 was ~8/8 hang under the same shape) but ~60% of
runs still hang.

## The residual is a PARK, not a spin (team's own 3-sample discriminator)
3x `thread apply all bt` over ~2s at a hang:
 - io_del_fd/__find_fd frames: 0  <-- the v1.40.7 spin is GONE.
 - stuck threads are in epoll_wait <- WaitEventSetWaitBlock <- backend_thread_run_worker,
   identical across all 3 samples -> genuinely PARKED (not looping).
 - NOTE: epoll_wait means the NON-fiber WaitEventSetWaitBlock branch (xtc_in_backend_fiber
   false) -> these are AUX WORKERS (walwriter/checkpointer/bgwriter run as pthreads) blocked
   in epoll, waiting on something the parked session fibers hold.
So the next question is what the SESSION fibers are parked on while the aux pthreads wait --
a different signature from all six prior surfaces.  Also notable: even the OK runs are only
~2.4-3.0k tps vs the stackless pool's 37.9k and fork's 46k, so the fiber path has a
throughput problem independent of the hang.
